## Stage 1 — shipped CLI execution gaps (closed)

Four defects were found only by executing the shipped command bodies:

1. **A JSON assignment could never be admitted.** `RunAssignment` requires
   `acceptance_argv` (and `entire_references`) to be tuples; JSON has no tuple
   type, so every documented `run --assignment card.json` failed with
   `invalid_assignment: acceptance_argv must be a non-empty tuple of argv
   strings` before any effect. Fixed at the CLI JSON boundary
   (`_assignment_payload`), with positive and negative tests.
2. **`resume` could not find the run's artifacts.** `run` accepts
   `--artifacts`; `resume` did not, so a resume in a new process probed the
   state directory and could not adopt the durable receipt. Flag added with the
   same default as `run`.
3. **No durable receipt across processes.** A real worker or reviewer that
   finished after the `run` process exited left no adoptable effect; `resume`
   needed a hand-written payload. `HermesWorker`/`HermesReviewer` now persist
   their attempt, transcript and result paths in the durable request, and
   `probe` proves completion from the child-written `result` event. Worker
   receipts derive from the result file or the committed workspace HEAD (dirty
   or unchanged is `failed`); reviewer receipts are re-audited from the
   transcript and bound to candidate/base/spec/evidence/graph. `resume` adopts
   that receipt when no payload is supplied, and holds with `effect_unknown`
   when completion cannot be proved.
4. **The implementation prompt did not name the spec.** A real worker had a
   digest but no file; the prompt now names the specification path and the
   check/commit contract.

`tests/test_orchestration_cli_e2e.py` executes the actual `run` and `resume`
commands as subprocesses against a stub board/worker/launcher: JSON assignment →
admitted run → persisted worker hold → duplicate-run refusal (one worker
request) → durable adoption on resume → installed gate → reviewer refusal

**Attempt 2 (2026-11-09, run 368/369): stopped before any effect — ownership
contract defect.** The pilot card's worker cannot hand the dispatcher grant to
the installed CLI. Measured in the attempt's own process: the three variables
`HERMES_KANBAN_TASK`, `HERMES_KANBAN_RUN_ID` and `HERMES_KANBAN_CLAIM_LOCK` are

one process above the CLI. Hermes deliberately strips it from tool children

`--attempt-run-id`/`--claim-lock` cannot substitute. The board's supported CLI
also does not expose the fencing token (`show --json` hides `claim_lock` and

## Stage 5 — measurement plan (defined before outcomes)

Cohort (fixed now, not after the fact): one normal card, one repair card, one
controlled-recovery card, each run through the installed release; definitions:

- *intervention*: a persisted hold (`awaiting_worker`/`awaiting_review`) or an
  operator cancel request observed in `inspect.metrics.interventions`;
- *stage diagnosis time*: time between the last stage event and the hold event;
- *stuck run*: a run with no stage transition for 15 minutes, or
  `effect_unknown`;
- *duplication*: more than one worker request per operation key, or a second
  write to the same workspace by a different process;
- *outcome*: `ready_for_authorized_completion` (with certified evidence and an
  independent approval) or the exact hold reason.

Baseline: no historical intervention/diagnosis measurements exist on this host
(`metrics.baseline.available = false`), so no improvement percentage is claimed.
Comparable legacy-path observations would have to be collected prospectively;
that was not done and is reported as a gap, not as a result. Attempt 1 supplies
one observed real-worker sample (46 s worker, 1 repair, 0 adopted interventions,
1 injected gate failure) and is labelled n=1.

Conditional expansion: only `factory-card/v1` on an enrolled card with a
certified installed acceptance and an attested independent review. Any other
workflow type, any missing gate or attestation, and any version mismatch stays
on the legacy path. Default-enabling is **not** proposed from n=1 evidence.
